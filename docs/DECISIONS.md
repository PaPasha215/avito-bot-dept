# Decisions Log

## 2026-02-16

### D-001: Область MVP
- Решение: отвечаем только по недвижимости.
- Причина: убрать риск ответов не в том контексте.
- Влияние: `AUTO/OTHER` всегда в `IGNORE_SILENT`.

### D-002: Режим отправки
- Решение: сразу боевой режим, без ручного апрува.
- Причина: учиться на реальных ошибках быстрее.
- Влияние: MessageProcessor отправляет ответ в Avito сразу.

### D-003: Лид-триггер
- Решение: лид создается только при наличии контакта.
- Причина: снизить шум и оставить только actionable заявки.
- Влияние: LeadDetector обязателен перед отправкой лида.

### D-004: Роутинг
- Решение: учитывать и мета контекст объявления, и текст диалога.
- Причина: мета не всегда надежна, диалог дает дополнительный сигнал.
- Влияние: RouterService использует `ad_category + classifier`.

### D-005: Хранилище
- Решение: SQLite локально, PostgreSQL на VPS.
- Причина: быстрый старт + простой путь к production-окружению.
- Влияние: `DATABASE_URL` через env-конфиг.

### D-006: Источник правды по Avito API
- Решение: использовать официальный OpenAPI из `https://developers.avito.ru/web/1/openapi/info/messenger`.
- Причина: публичные страницы каталога рендерятся динамически, а endpoint `/web/1/openapi/*` дает точную актуальную схему.
- Влияние: подтвержден рабочий формат `POST /messenger/v1/accounts/{user_id}/chats/{chat_id}/messages`.

### D-007: Ошибки lead-пайплайна не должны дублировать ответы в Avito
- Решение: исключения на этапе summary/Telegram не должны фейлить весь event после успешной отправки ответа в Avito.
- Причина: иначе event остается `FAILED` и может повторно отправлять ответ клиенту.
- Влияние: lead-пайплайн обернут в безопасную обработку ошибок, а основной event доходит до `PROCESSED`.

### D-008: Догрузка burst-сообщений с fallback endpoint
- Решение: при чтении истории чата сначала использовать `v3/messages`, а при `402/404/405` пробовать `v1/messages`.
- Причина: часть чатов возвращает `402` на `v3`, что приводило к риску пропуска быстрых последовательных входящих сообщений.
- Влияние: улучшена полнота инжеста в реальном времени без изменения основного polling endpoint (`v2/chats`).

### D-009: Операционная диагностика по external_chat_id
- Решение: добавить единый endpoint/CLI для полной диагностики чата (messages, routing, replies, leads, feedback, event logs).
- Причина: быстрый разбор инцидентов без ручных SQL-запросов.
- Влияние: сокращено время дебага и снижена зависимость от ручной проверки БД.

### D-010: Самообучение через поведенческие примеры, а не онлайн fine-tune
- Решение: внедрить `SelfLearningService` с nightly-циклом, который извлекает правила/примеры из успехов и ошибок и подмешивает few-shot контекст в системный промпт.
- Причина: безопаснее и быстрее для MVP, чем автопереобучение модели; легко откатывается.
- Влияние:
  - добавлены таблицы `learning_examples` и `learning_reply_usage`;
  - добавлен canary rollout (`active/stable`) и автоматический rollback/promotion по KPI;
  - добавлена команда `learn-once` и автозапуск цикла из poller по интервалу.

### D-011: Миграция на Jino VPS через PostgreSQL
- Решение: стандартный production-контур — Docker Compose + PostgreSQL, перенос локальной SQLite одноразовым скриптом.
- Причина: сохранить историю/лиды при переезде с локального окружения и избежать ручного SQL.
- Влияние:
  - добавлен скрипт `scripts/migrate_sqlite_to_postgres.py`;
  - обновлен `deploy/docker-compose.vps.yml` (volume для `/app/data`);
  - подготовлен runbook `docs/DEPLOY_JINO.md`.

### D-012: Для Jino VPS нужен LLM endpoint с поддерживаемым регионом
- Решение: не использовать прямой OpenAI egress с текущего Jino VPS, пока он дает `403 unsupported_country_region_territory`; использовать OpenAI-совместимый endpoint/прокси или другой VPS-регион.
- Причина: с текущего IP бот не может вызвать `chat/completions`, значит не может отвечать в Avito.
- Влияние:
  - для прода требуется перенастройка `OPENAI_BASE_URL`, `OPENAI_API_KEY`, `OPENAI_MODEL` (или смена VPS/egress);
  - до этого момента polling/логика БД работают, но генерация ответа блокируется.

### D-013: Временный production LLM-провайдер — OpenRouter
- Решение: переключить текущий прод на OpenRouter (`/api/v1`) с моделью `openai/gpt-4o-mini`.
- Причина: сохранить текущий Jino VPS и восстановить генерацию ответов без миграции инфраструктуры.
- Влияние:
  - `.env` на VPS обновлен (`OPENAI_BASE_URL`, `OPENAI_MODEL`, `OPENAI_API_KEY`);
  - polling снова включен;
  - подтвержден успешный тест `chat/completions` (`HTTP 200`) с VPS.

## 2026-02-17

### D-014: Детерминированные guardrails для диалога по недвижимости
- Решение: добавить в `MessageProcessor` кодовые правила до вызова LLM:
  1. уточнение короткого бюджета (`8-12`, `8р-12р`, `812`) как тысячи рублей в месяц;
  2. специальный ответ на "куда вам набрать" без выдачи прямого номера менеджера;
  3. мягкий первый ответ в новом чате: приветствие + вопрос об актуальности заселения.
- Причина: снизить количество "навязчивых" и контекстно-неверных ответов, а также исправить типовые сценарии из реальных диалогов.
- Влияние:
  - критичные сценарии теперь не зависят от вариативности LLM;
  - уменьшен риск потери лида из-за некорректной интерпретации краткого бюджета;
  - первый контакт стал более естественным и менее агрессивным.

### D-015: Усиление контекста объявления в runtime-промпте
- Решение: при генерации ответа добавлять в системный промпт явный контекст `ad_title/ad_category` и правила "не уходить из фокуса объявления".
- Причина: в части чатов модель задавала лишние вопросы вне контекста конкретного объявления (например, общий опрос при объявлении "койко-место").
- Влияние:
  - выше релевантность ответов к текущему объявлению;
  - меньше лишних уточнений "хостел/квартира/койко-место" без необходимости.

### D-016: Компактный формат Telegram lead-card
- Решение: сократить размер lead-card (summary и меньше реплик контекста), без дополнительной клавиатуры.
- Причина: уменьшить визуальную перегрузку рабочих чатов менеджеров.
- Влияние:
  - сообщения в Telegram стали короче и легче для быстрой обработки;
  - подготовлен более аккуратный UX под следующий этап CRM-статусов.

### D-017: Ежедневный авто-отчет по объявлениям в Telegram
- Решение: добавить сервис `StatsReportingService`, который раз в сутки формирует и отправляет в Telegram сводку:
  1) топ по охвату (views),
  2) топ по конверсии (views->contacts) при достаточном трафике,
  3) кандидаты на переработку (много views, низкая конверсия).
- Причина: перейти от ручного разбора к регулярному data-driven улучшению объявлений.
- Влияние:
  - добавлены настройки `STATS_REPORT_*` и `TELEGRAM_STATS_CHAT_ID`;
  - добавлен ручной запуск `make stats-report-once`;
  - отчет выполняется автоматически через цикл poller по интервалу.

### D-018: Weekly anti-spam расписание и формат отчета
- Решение:
  1. автоматический отчет отправлять только по расписанию: понедельник 09:00 (`Asia/Yekaterinburg`) один раз в неделю;
  2. отчет строить за предыдущую календарную неделю (понедельник-воскресенье);
  3. формат отчета полностью на русском;
  4. из отчета исключать нерелевантные категории (оставлять только объявления недвижимости).
- Причина: убрать спам и синхронизировать отчет с еженедельной утренней встречей.
- Влияние:
  - добавлены настройки расписания: `STATS_REPORT_WEEKDAY`, `STATS_REPORT_HOUR`, `STATS_REPORT_MINUTE`, `STATS_REPORT_TIMEZONE`;
  - изменена логика `run_if_due` в `StatsReportingService`;
  - улучшена релевантность и читаемость отчета.

### D-019: Диалог без повторного вопроса «актуально ли» при явном запросе
- Решение: если клиент уже в первом сообщении явно пишет про заселение/наличие/даты/бюджет, бот не задает повторный вопрос об актуальности, а сразу задает следующий квалифицирующий вопрос.
- Причина: убрать лишний шаг в диалоге и повысить конверсию в контакт.
- Влияние:
  - добавлена детекция явного намерения заселения;
  - добавлена пошаговая квалификация (даты -> количество человек -> бюджет -> контакт);
  - добавлен guardrail против «уточню у менеджера» без сбора контакта.

## 2026-02-18

### D-020: Жесткие правила посуточного/помесячного размещения по адресам
- Решение:
  1. посуточное размещение разрешено только для 3 хостелов:
     - Куйбышева, 30 («Сити Е»),
     - Мамина-Сибиряка, 132 («В гостях у бабуси»),
     - Ботаническая, 30 («Уютное местечко»);
  2. для остальных объявлений бот ведет клиента в помесячный сценарий;
  3. при вопросе о цене бот дает только ориентир и добавляет, что точную цену подтверждает менеджер.
- Причина: единые коммерческие правила и меньше ложных обещаний в чате.
- Влияние:
  - добавлены rule-based проверки short-stay + распознавание хостельных объявлений по адресу/названию;
  - добавлен шаблонный ответ по ориентиру посуточной цены в хостеле (`от 700 ₽/сутки`).

### D-021: Анти-абьюз фильтр в реальном времени
- Решение: входящие с оскорблениями/угрозами/обвинениями/эскалацией в надзорные органы переводятся в `IGNORE_SILENT`.
- Причина: снизить операционный шум и не вступать в токсичные ветки автоответом.
- Влияние:
  - добавлен детерминированный фильтр `ABUSE_OR_THREAT`;
  - такие события логируются в `routing_decisions` с причиной `ABUSE_OR_THREAT`.

### D-022: UI-курс на двухуровневое Telegram-меню
- Решение: для внешнего Telegram-интерфейса (не текущий Avito-бот backend) проектируем двухуровневую навигацию без "портянок" кнопок.
- Причина: текущий интерфейс перегружен и замедляет работу менеджеров.
- Влияние:
  - создано отдельное ТЗ в `docs/TELEGRAM_MENU_2LEVEL_TZ.md`;
  - реализация выделена в следующий этап.

### D-023: Стратегия подключения новых площадок через readiness-gate
- Решение: перед реализацией каждого нового marketplace-коннектора проходить формальный checklist из `docs/CONNECTOR_READINESS_CHECKLIST.md`.
- Причина: не тратить время на каналы без доступного chat API и заранее фиксировать интеграционные риски.
- Влияние:
  - приоритет подключения: Avito (active) -> Циан (кандидат) -> Юла/Яндекс.Недвижимость (feed-first до подтверждения chat API);
  - каждый новый коннектор открывается только после подтверждения авторизации, chat endpoints, лимитов и ToS.

### D-024: Старт Youla по схеме feed-first + readiness
- Решение: начать Youla поэтапно:
  1. зафиксировать config/CLI readiness в проекте;
  2. использовать предоставленные Youla Swagger ссылки (`/swagger/rapi`, `/swagger/ui`) как базовую точку валидации;
  3. запросить официальные chat API доступы у Youla;
  4. до получения chat API использовать режим `feed_only`.
- Причина: избежать "слепой" разработки интеграции без подтвержденных endpoint'ов.
- Влияние:
  - добавлены env-параметры `YOULA_*` и команда `validate-youla-readiness`;
  - добавлены документы `docs/YOULA_ONBOARDING.md` и `docs/YOULA_SUPPORT_REQUEST_TEMPLATE.md`.
